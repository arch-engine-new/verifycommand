## 1. 背景与目标

### 1.1 背景
- 首筑旗下某 APP 已使用银联商务支付能力（微信直连），但**耦合在单一 APP 内**，无法复用到其他业务。
- 首筑物业 C 端 APP 需支持业主线上缴纳**物业费、停车月租费**。
- 物业公司是 N 个独立商户主体，未来会有大量物业公司接入，**必须走可复制的通道模式**。

### 1.2 目标
1. 建设可复用的**支付中心**（对业务系统提供统一支付能力，业务系统不感知底层通道）。
2. **2 周内**支撑首筑物业 C 端 APP 缴费上线（APP 原生支付组件直驱银联 SDK，**无自建收银台**）。
3. **多物业公司可扩展**：新增物业 = 新增商户配置 + 银联子商户进件，支付中心与 C 端零改动。
4. **分账就绪**：一期全额结算给物业，接口与数据模型预留分账字段，二期无缝切换分账抽佣。

### 1.3 非目标（一期不做，详见 08-功能两期拆分.md）
- 对账中心、费率体系、结算试算、三级开关管理后台、运营后台完整版（一期仅商户配置最小入口 + 交易查询）
- 退款审核工作流（一期退款由运营/B 端发起，C 端退款申请入口二期）
- 多账单合并支付（一期单账单）
- 电子凭证独立页、催缴模块、监管数据报送
- 小程序/H5 独立入口、自建收银台页面（一期 C 端直驱银联 SDK；小程序/H5 入口二期）
- 银联分账业务启用（仅预留字段）
- 停车临停/无感支付/动态计费
- POS、扫码（B 扫 C/C 扫 B）、对公转账、企业网银
- 支付路由、独立风控引擎、自动调账
- 商户自助进件后台（一期运营手工配置）

## 2. 名词术语

| 术语 | 说明 |
|---|---|
| 支付中心 | 首筑自建统一支付服务（本期交付物） |
| 业务系统 | 调用支付中心的服务方（本期：物业 C 端 APP、B 端物业系统） |
| C 端支付组件 | C 端 APP 原生支付方式选择页 + 银联 SDK 调起（**无自建收银台**） |
| 支付单 | 支付中心一次支付请求记录（一期单账单；二期支持一单多账单） |
| 退款单 | 支付中心一次退款请求记录 |
| 商户/子商户 | 物业公司在银联侧的收单主体；首筑为主商户（服务商侧） |
| 通道 | 支付渠道（一期：银联商务） |
| 支付方式 | 微信、支付宝、银行卡/云闪付（借记/贷记不区分，统一走银联统一收银台；成交卡种以银联回传 cardAttr 记录），均挂在一个通道下 |
| 异步通知 | 银联支付结果回调 + 支付中心向业务系统的支付结果回调 |
| 分账 | 按规则将交易资金拆分给多个主体（一期预留，二期启用） |

├────────────────────────────────────────────────┤

│  └───────────────┘  └───────────────────┘      │
│  ┌───────────────┐  ┌───────────────────┐      │
│  │ 支付参数下发    │  │ 对账/费率/开关后台  │      │
│  │ (pay_params)   │  │ (二期)             │      │
│  └───────────────┘  └───────────────────┘      │

│  ┌───────────────────┐                          │
│  │ 银联商务适配器     │  ← 唯一真实通道（一期）   │
│  └───────────────────┘                          │
├────────────────────────────────────────────────┤

**扩展点**：
- 新通道接入 = 新增适配器（易宝/通联二期接入，作通道切换备选），核心不动；切换开关一期就位
- 分账启用 = 下单/退款报文携带 satInfo/divisionFlag + 银联分账配置，二期启用
- 停车临停 = 新增"代扣"接口位（微信服务商委托代扣），二期实现
- 线下扫码（B 扫 C/C 扫 B）= 通道抽象预留 Native 扫码收单接口位 + 支付方式枚举预留 SCAN，二期实现（试点物业前台扫码缴费）

## 4. 角色与核心场景

| 角色 | 说明 | 关键动作 |
|---|---|---|
| 业主 | 小区住户 | 查看账单 → 缴费 → 查看记录/凭证 → 申请退款 |
| 物业公司 | 商户主体 | B 端配置账单、审核退款、查看收款 |
| 首筑运营 | 支付中心管理 | 商户配置、费率配置、通道开关、对账核销、异常处理 |
| 银联商务 | 通道方 | 收单、清算、子商户管理 |

核心场景：
- S1 业主缴物业费（月/季/年，按 B 端账单）
- S2 业主缴停车月租费（按车位个数计费，B 端账单）
- S3 业主申请退款（错缴/重复缴），物业审核后原路退回
- S4 运营对账核销（每日）
- S5 通道异常降级（微信不可用 → C 端支付方式页不展示微信，支付宝/银联卡照常）

## 5. 核心业务流程

### 5.1 缴费主流程

```
B 端物业系统生成账单（物业费/停车月租）
  → 账单入库（含物业公司标识、业主标识、金额、周期）
C 端 APP 展示账单列表/详情（业主登录后按房产/车位聚合）
  → 业主选择账单 → 调支付中心【创建支付单】
支付中心：
  → 校验商户配置/账单金额 → 生成支付单（待支付）
  → 调银联【下单】→ 获取支付要素 → 返回 pay_params
C 端 APP 原生支付方式页 → 业主选定支付方式 → 调【创建支付单】(携 pay_method)
  → 得 pay_params → 银联 SDK 调起（微信 App 支付/支付宝/银联收银页）
  → 支付完成 → 回跳 return_url → APP 调查单确认
银联【异步通知】→ 支付中心验签 → 支付单→支付成功
  → 支付中心【业务回调】→ C 端/B 端
  → B 端账单标记已缴 → C 端展示结果页
```

### 5.2 退款流程

```
物业/运营在 B 端发起退款（C 端业主退款申请入口二期）
  → 物业公司审核（可退金额、原因）
  → 调支付中心【创建退款单】（原支付单 + 退款金额，一期仅全额）
支付中心调银联【退货】→ 原路退回
  → 银联【退款通知/退款查询】→ 退款单状态更新
  → 【业务回调】→ B 端账单更新（部分退/已退）
```

**退款时效与规则（银联答复确认）**：
- 原路退回：退零钱/余额**准实时**；退银行卡看各银行处理时效（0-3 个工作日参考）
- **退款时限最大 360 天**（原支付成功之日起，银联答复确认）；单笔订单最多 **50 次退款**，累计不超交易金额（一期全额、二期多次部分退）
- **手续费处理**：**退款会返还手续费**（已结算退款按比例返还，未结算轧差）——退款单需记录 refund_fee_return，二期对账核对
- 渠道返回"退款成功"仅表示**收到退款请求**，并非已上账——C 端/B 端展示"到账时效以渠道实际入账为准"
- 商户资金不足（已结算退款场景）→ 退款失败，需分类提示"可用余额不足"（一期全额退款走未结算轧差，基本不触发，但退款失败处理要留该错误分类）

### 5.3 订单关闭
业主发起支付后超时未完成（默认 15 分钟，可配置）→ 支付中心调银联【订单关闭】，支付单 → 已关闭。

### 5.4 对账主流程（二期实现，一期以超时查单任务兜底）
```
T 日终 → 拉取银联对账文件 → 解析入库
  → 与本地支付单/退款单比对（单号/金额/状态/笔数）
  → 差异列表 → 人工核销 → 平账归档
```

## 7. 状态机

### 7.1 支付单状态机

```
创建 → WAIT_PAY（待支付）
WAIT_PAY ── 支付成功（通知/查询）──→ PAID（支付成功）
WAIT_PAY ── 超时/主动关闭 ──→ CLOSED（已关闭）
PAID ── 发起退款 ──→ REFUNDING（退款中）
REFUNDING ── 全额退款成功 ──→ REFUNDED（已退款）
REFUNDING ── 退款失败 ──→ PAID（回退，可再次发起退款）
REFUNDING ── 部分退款成功 ──→ PAID（部分退，金额字段记录已退，二期）
（异常态：UNKNOWN 未明确 → 由"超时查单后台任务"+查询接口收敛；长期未收敛以对账兜底）
```

**状态总表（唯一口径，02/04/10/20/22 均以此为准）**：

| 对象 | 状态码 | 含义 | 可迁移到 | 触发方 |
|---|---|---|---|---|
| 支付单 | WAIT_PAY | 待支付 | PAID / CLOSED | 创建 |
| 支付单 | PAID | 支付成功（含部分退款后，已退金额记 refunded_amount） | REFUNDING | 银联通知 / 查单 |
| 支付单 | REFUNDING | 退款中 | REFUNDED / PAID（失败或部分退回退） | 发起退款 |
| 支付单 | REFUNDED | 已全额退款（终态） | — | 退款成功 |
| 支付单 | CLOSED | 已关闭（终态） | — | 超时任务 / 主动关闭 |
| 退款单 | REFUNDING | 退款中 | REFUND_SUCCESS / REFUND_FAIL | 创建 |
| 退款单 | REFUND_SUCCESS | 退款成功（终态） | — | refund-query 明确 SUCCESS |
| 退款单 | REFUND_FAIL | 退款失败（终态，可新建退款单重试） | — | refund-query 明确 FAIL |

- 银联 UNKNOWN / PROCESSING **不是我方状态**，只触发补查，我方状态保持不变。
- 「需人工核查」**不是状态**，是支付单 / 退款单上的标记字段 `manual_check`（连续 3 轮定时查单仍未明确时置位并告警），运营后台可筛选。
- 一期部分退款不开放（全额退款），状态机预留。

**支付失败语义（重要，避免状态机与页面冲突）**：
- 用户取消/渠道支付失败（如余额不足、取消授权）→ **支付单仍为 WAIT_PAY，不落 FAIL 终态**；C 端"支付失败"只是页面展示态，可重试
- 重试方式：**复用原 mchntOrderId 重新调起支付**（银联侧同单号可重复调起）；若银联拒绝重复调起，则先走"关闭支付单"（02 §3.8）再创建新单
- 银联应答失败但渠道可能已扣款（状态未知）→ 一律进查询兜底（FR-15），**严禁直接标记失败**

**后台兜底任务（必建）**：
- **超时查单任务**：每 5 分钟扫描 WAIT_PAY 且创建超 2 分钟未收敛的支付单，调银联支付查询；连续 3 次 UNKNOWN 置"需人工核查"并告警——**这是对账上线前唯一的最终兜底，一期必须实现**
- **超期关闭任务**：扫描超过 expire_time 仍未支付的 WAIT_PAY 单 → 本地置 CLOSED 并调银联 order-close（尽力而为）——**防止"用户调起支付后中断（杀进程/切后台未回）"导致支付单永远悬挂**

### 7.2 退款单状态机

```
创建 → REFUNDING（退款中）
REFUNDING ── 退款成功 ──→ REFUND_SUCCESS
REFUNDING ── 退款失败 ──→ REFUND_FAIL（可重试）
REFUNDING ── 未明确 ──→ 轮询/查询兜底
```

### 7.3 未明确状态两层兜底（唯一口径）

| 层 | 支付 | 退款 |
|---|---|---|
| 第一层：即时补查（延迟队列） | 下单 / 查单返回 UNKNOWN 或非 0000：5s / 30s / 60s 调 online/query | 退款返回非 SUCCESS/FAIL：5s / 30s / 60s / 5min 调 online/refund-query |
| 第二层：定时任务 | 每 5 分钟扫 WAIT_PAY 且创建超 2 分钟未收敛单 → online/query | **每 5 分钟扫 REFUNDING 超 10 分钟未收敛退款单 → online/refund-query**（一期新增） |
| 告警 | 第二层连续 3 轮仍未明确 → 置 manual_check + 告警 | 同左 |
| 超期关闭 | 超 expire_time 的 WAIT_PAY → 本地 CLOSED + 尽力调 order-close | — |

第一层先跑完再由第二层接管；「连续 3 轮」按第二层轮次计数。

## 10. 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | 下单接口 P95 < 500ms；查询 P95 < 300ms |
| 可用性 | 支付中心 ≥ 99.9%；银联故障时 C 端支付方式自动降级（3.9 不返回故障方式） |
| 幂等 | 创建支付单按 biz_order_no 幂等；通知处理幂等（重复通知不重复入账） |
| 安全 | 与银联 OPEN-BODY-SIG 签名验签；业务系统 API 签名鉴权；金额防篡改（金额由服务端锁定，回调以银联返回为准）；pay_params.app_pay_request 服务端透传禁止客户端改动；敏感数据脱敏 |
| 审计 | 关键操作留痕（状态变更/配置变更/核销操作） |
| 合规（重庆） | 收费明码标价公示（账单明细可溯源）；前期物业费指导价约束（B 端出账）；停车费按车位个数；公共收益涉共有车位时按条例公示（B 端配合） |
| 扩展性 | 通道适配器模式；支付方式枚举配置化；费率表化；分账字段预留；对账按通道维度扩展 |
